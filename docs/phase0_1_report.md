### 採用した 3 つの変更点（`v0221_opt_bench` → `v0221_p1_best`）
1. **`--spec 4` → `--spec 6`（`--draft-conf 0.7` 維持）**: `dflash2_max_window` が `6 → 8` に拡張され、コード等の予測しやすい領域で大幅加速。
2. **`STRATA_ADAPT_NOWAIT=1` を削除**: `v0.2.20` 以降の適応キャッシュの非同期オーバーラップを阻害していた旧フラグを除去し、キャッシュヒット率・速度ともに改善。
3. **`STRATA_GDN_SPLIT=1` を追加**: `v0.2.21` で追加された GDN レイヤーの列分割カーネルを有効化し、特に日本語生成・中長文 Decode を底上げ。

## 2. Phase 0：ソース棚卸し・プロファイリング結果

`v0.2.21` のソースコードおよび起動ログ・`/proc/<pid>/smaps_rollup` から以下を確認しました：

1. **HugePages はすでに適用済み**:
   - Expert Arena（`46.84 GiB`）は `MADV_HUGEPAGE` により **`AnonHugePages: 49,096,704 kB`（約 46.8 GiB / 約 95%）** が 2MB THP として確保済み。静的 HugePages 予約（`vm.nr_hugepages`）は空き RAM 5 GiB 環境では不要と判断。
2. **候補フラグの実在・デフォルト確認**:
   - `STRATA_ADAPT_FETCH=2` は `nv_defaults.cpp` により 16 GiB カード（`sm_89`）でデフォルト有効。
   - `STRATA_IQ256_GATHER` は未設定時、本家が **Pコア／Eコアごとのスレッド単位で Gather 方式を自動選択**。
   - `STRATA_L3_PF` は `<= 13 GiB` VRAM のみ自動有効であり、RTX 4080 (16 GiB) では未適用だった。
   - `STRATA_ADAPT_NOWAIT=1` を手動指定していたせいで `adaptive overlap: off: not with STRATA_ADAPT_LAG / STRATA_ADAPT_NOWAIT` と出力され、新世代の適応キャッシュ機構と干渉していた。
   - `CPU pool tasks/phase: 72 (automatic)`（24 参加スレッド × 3 タスク/phase）で動作。
   - `perf stat` はカーネルの `perf_event_paranoid=4` 制限により一般ユーザーではハードウェアカウンタ取得不可（`sudo` なし環境）。

## 4. 運用上の注意点と Phase 2 以降の提言

1. **空き VRAM マージンについて**:
   - `--spec 6`（`dflash2_max_window: 8`）の CUDA Graph 増加により、17.6K 負荷後の空き VRAM が `89 MiB` → **`31 MiB`** に詰まっています。今回の 17.6K ストレスおよび 16問品質テストは OOM なしで完走しましたが、もし将来 Vision 同時利用や別アプリ併用で窮屈になる場合は `--vram-reserve-mib 96 → 128` へ戻すことで安全マージンを確保できます（スロット減は約 16 個 / 0.3% のみ）。
2. **Phase 2 以降（155〜170+ tok/s を狙う場合の次ステップ）**:
   - 今回の実験で **`STRATA_L3_PF=1` が DDR5-4000 帯域競合で逆効果**、**`STRATA_POOL_STATIC=1` が Eコア待ちで逆効果** であることが実証されました。
   - これにより、残るボトルネックは **① DDR5-4000 の実効メモリ帯域** と **② Pコア／Eコア混在の動的タスク配分（Weighted / Guided Scheduling）** に絞り込まれました。
   - ソフトウェア改造で次に取り組むなら **Phase 2（P/E 非対称スケジューリング＋LTO ビルド）**、ハードウェア／BIOS 側で最も費用対効果が高いのは **RAM の XMP 有効化（DDR5-4000 → 5600〜6000+）** または **CPU ターボの上限付き解放（4.0〜4.5 GHz キャップ）** です。
